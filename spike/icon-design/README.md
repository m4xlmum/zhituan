# 图标方案

这套稿子给「纸团」重做应用图标，产出 8 套供选。**选中的那一套**再用
`make_ico.py` 落成 `build/icon.ico`、`build/icon.png`、`resources/tray.ico`。

## 链路：Python 产 SVG  ->  Chrome 栅格化  ->  纯标准库打 ICO

```
python icons.py            # 出 out/svg/*.svg、out/board.html
python shoot.py --board     # out/board.html -> out/board.png（对比板）
                            # out/svg/*.svg  -> out/png/<方案>-<尺寸>.png（六档，透明底）
python make_ico.py A        # 把方案 A 打成三个 ico/png
```

`shoot.py A F` 可以只重出某几套。

没有引任何依赖，两个原因：

- **Electron 在这台机器上跑不起来**。用项目自带的 `node_modules/electron` 起渲染
  进程会被执行环境掐掉（SIGTERM），`--no-sandbox --in-process-gpu` 也一样 ——
  而上一轮探针还能跑，所以这不是参数问题。另有一个坑：环境里设了
  `ELECTRON_RUN_AS_NODE=1`，`VAR=` 这种空值前缀清不掉它（判的是「存在」而非真值），
  得用 `env -u ELECTRON_RUN_AS_NODE`。
  （**2026-09-30 补一句**：这里写的 `env` 在本机 PATH 上被 `~/.local/bin/env` 遮住了
  ——那是一份 328 字节的 shell 片段，不看参数也不执行后面的命令，于是 `env -u …` 全程
  空转、退出码 0。要清得写成 `/usr/bin/env -u …`，或者用 shell 内建的 `unset`。
  详见 [docs/verification.md](../../docs/verification.md) 开头那一段。）
- **Pillow 装不上**。pypi 官方源下载 7.2MB 卡在代理上（约 35KB/s，十分钟没动），
  清华源直接返回 `from versions: none`。

还有一条：项目路径里那六个汉字会让 Electron 的 `loadFile` 直接 `ERR_FAILED(-2)`
（它拼出来的 URL 带反斜杠）。Chrome 无头不受影响。

## 渲染：一条正路，七个坑

用户第一次看到的「图标都是一半一半的」就是这里来的，所以把踩过的都记全。

**最终做法**：Chrome 只负责把 **256×256** 画出来（每方案两个变体，共 16 次调用），
16/32/48/64/128 由 Python 做**面积平均降采样**得到。理由有两层——小尺寸由重采样
出来比让 Chrome 直接画 16px 更平滑；以及 Chrome 在别的尺寸上根本不听话。

| # | 坑 | 症状 / 解法 |
|---|---|---|
| 1 | 直接截 SVG 文件 | Chrome 按 SVG 的**固有尺寸**排版，`icons.py` 的 SVG 只有 viewBox（512），开 256 窗口只截到左上角 → **「图标都是一半一半的」** |
| 2 | 套 HTML 用 `100vw / 100vh` 撑满 | `--window-size` 只决定**输出 PNG 的尺寸**，页面视口是另一个值（`innerWidth/innerHeight` 实测 **500×105**）。`100vw = 500px`，图被放大两倍，照样残 |
| 3 | 只渲染 256 这一档 | 图标写成固定像素、贴左上角是唯一可靠的画法，但 **128 档仍然坏**（内容只剩顶部 33 行，原因没查出来）→ 干脆只信任 256 |
| 4 | 包装页固定文件名 | 反复覆写同一个 `_shot.html`，Chrome 命中 file:// 缓存，拿到**上一次**写进去的页面 → 每次换唯一文件名 |
| 5 | profile 目录复用 | 目录已存在时新起的 Chrome 被「复用实例」，命令行被转发给还活着的那个 → 每次换唯一 profile |
| 6 | `--screenshot` / `--user-data-dir` | 前者只吃**绝对路径**；后者不给是**静默失败**（退出码 0、不产文件）；前一个进程没退干净就起下一个也会静默不产文件 |
| 7 | 中途删文件 | 删除会被执行环境的 safe-delete 拦（每个用户请求累计额度 **50 个**），脚本半路被 SIGTERM，症状是**前半程正常、后半程全是旧文件** → 中间物一概不删，全扔系统临时目录 |

像素真伪靠 `shoot.py` 的 `read_png`（纯标准库解 PNG，含 filter 还原）抽查：
不透明像素占比低于 60%、或内容包围盒没铺满，当场判坏。透明底靠
`--default-background-color=00000000`（产出的 PNG 是 ctype=6 RGBA）。

## 造型：四条错路，一条留下

「纸团」这个造型在扁平矢量里比想象中难。以下四条都做出来看过，都不是纸团：

| 画法 | 结果 |
|---|---|
| 12 个均匀顶点 + 从中心放射的三角面 | **切割宝石** —— 所有面共用一个中心点，那就是刻面的定义 |
| 三条弦把多边形切成 4 片，硬边填色 | 大小合适了，但大色块读出来是**折纸** |
| 5 层同源多边形由大到小叠上去 | 小图还行，放到 512 就是**洋葱 / 螺旋** |
| 32~58 个内部点做三角剖分（low-poly） | 有质感，但无论怎么调明暗都读成**石头** |

再加折痕线试过两次：细折线是划痕，三条交叉是十字伤疤。

**留下的那一条**：外剪影 + 内层一块（偏心，读成翻折的一层）。理由是扁平、干净，
而且 16px 与 512px 是同一个形状 —— low-poly 那种细节到 16px 只会糊成噪点。
本次的结论是：在扁平矢量里，「揉皱」这个信息只能靠**很少几条折痕**带，细节一多就成石头。

所以严格讲，A/B/C/E 这几枚更接近「一团被摊开的纸」，而不是一颗揉紧的纸团。
真正让人一眼认出来的是 **F（两张纸 · 透明）**——它把产品的机制（窗口可逐像素透明）
直接画了出来，不靠「纸团」这个双关。

## 每个方案的两个变体

```
big   带内层，用于 >= 48px
mini  纯剪影，用于 <= 32px
```

对比板上「尺寸」那一栏，64/48 用 big、32/16 用 mini；16 与 32 才是任务栏和
Alt+Tab 的真实大小，认不认得出看那一栏。

## 文件

```
icons.py         几何与方案定义（唯一真相源）
shoot.py         栅格化：SVG -> 各档 PNG（透明底），也能重出对比板
make_ico.py      打包成 ico（纯标准库写 ICO，PNG 内嵌）
out/board.html   对比板（Chrome 截图的输入）
out/board.png    对比板成品
out/svg/*.svg    单个方案，可直接用浏览器打开
out/png/*.png    各方案六档（16/32/48/64/128/256），make_ico.py 的输入
```
